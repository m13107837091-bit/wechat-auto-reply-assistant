## 1. 背景

### 1.1 现在的形态

你现在已经有一套**能工作的**系统：

```
[微信 PC 客户端] <--- UI 自动化（写） ---┐
       │                                │
       └--- SQLCipher 解密（读） ---> [Python 后端]
                                        ├─ LLM 调用（DeepSeek）
                                        ├─ 会话记忆（8 轮 / 1 小时）
                                        └─ 策略（黑白名单 / 夜间静默 / 限速）
                                        │
                              [标准库 http.server]
                                        │  http://0.0.0.0:8000
                     ┌──────────────────┴──────────────────┐
              [手机浏览器 + Tailscale]            [Tauri 壳（多余）]
```

### 1.2 为什么你"感觉不是在用软件"

三个具体原因，每条都有代码依据：

1. **没有实体。** 电脑上只有 `pythonw.exe` 一个后台进程，进程列表里它叫 "pythonw" 而不是一个软件名；而且是**无控制台**版本，崩了你也不知道。依据：`scripts/backend-loop.ps1:21` 直接写死 conda 路径去拉 `pythonw.exe`。
2. **靠外部机制挂起来的。** 自启 = Windows 计划任务 + 一个 `.ps1` 无限循环。这不是软件自带的能力，是手工挂上去的。依据：`scripts/install-autostart.ps1`。
3. **界面是网页，壳是空的。** Tauri 窗口的全部内容就是加载 `http://127.0.0.1:8000/?token=...`，它没有自己的任何 UI。依据：`desktop/src-tauri/src/lib.rs:211`。

**结论**：你的直觉准确。当前形态是「**一个网页 + 一套运维脚本**」，不是「一个软件」。

### 1.3 不可绕过的约束

> **个人微信没有官方消息接口。** 腾讯禁止第三方自动收发个人微信消息。

要"读"和"写"，只有三条路：

| 路 | 可行性 |
| --- | --- |
| 本地库解密读 + UI 自动化写（现状） | ✅ 零封号风险，但需要一台常开的 Windows |
| 安卓通知通道 | ✅ 不需要电脑，但只有单条消息、无上下文 |
| 逆向协议 | ❌ 封号风险高，明确不做 |

前两条都要求**有一台机器 7×24 常开**。

**所以无论怎么改造，"家里那台电脑必须开着、微信必须登录着"这一条去不掉。** 这是本方案的前提，你已确认接受。

## 4. 目标架构

### 4.1 改造后

```
        ┌─────────────────────────────────────────────┐
        │  wechat-bot.exe（托盘程序 = 主进程）          │
        │                                             │
        │  主线程 : 托盘消息循环 + 菜单 + 气泡通知      │
        │  线程 A : HTTP 面板服务（0.0.0.0:8000）      │
        │  线程 B : 自动回复循环（现有 controller）     │
        │  线程 C : 微信客户端 / 后台任务               │
        └─────────────────────────────────────────────┘
                 │                          │
         [手机 PWA / 浏览器]        [微信 PC 客户端]
```

**关键点**：后端、托盘、面板进**同一个进程** → 不再有"谁拉起谁"的问题，也不再有一个裸的 `pythonw.exe` 待在进程列表里。

### 4.2 关键变化对照

| | 现在 | 改造后 |
| --- | --- | --- |
| 电脑上看到 | 进程列表里的 `pythonw.exe` | 托盘一个图标「微信自动回复」 |
| 崩溃可观测 | 无（无控制台） | 托盘气泡 + 面板错误条 |
| 打开面板 | Tauri 窗口 | 默认浏览器 / 托盘菜单 |
| 自启 | 计划任务 → `.ps1` → `pythonw` | 计划任务 → `wechat-bot.exe` |
| 依赖环境 | 整个 conda 环境 | 单 exe（批次 4 达成） |
| 手机端 | 普通网页 | 主屏幕图标 + 全屏观感 |
| 你能看到的回复 | 只有日志，还截断 40 字 | 面板「最近动态」卡片（全文） |

> ⚠️ 上面 4.1 那张图是 **D1① 的形态**（单进程 Python + 托盘）。你已选 **D1②**，实际形态见 **4.3**。

### 4.3 D1 选②之后的实际形态

```
┌──────────────────────────────────────────────────┐
│ desktop.exe（Tauri / Rust）                       │
│   ├── 系统托盘：菜单 / 状态图标 / 气泡通知          │
│   ├── 主窗口：WebView 加载 http://127.0.0.1:8000  │
│   └── 子进程：pythonw.exe src/main.py             │
│                 └── HTTP 面板 + 自动回复循环       │
└──────────────────────────────────────────────────┘
```

与 D1① 的区别：**托盘和窗口都在 Rust 侧**，Python 仍是子进程。
好处是观感原生、窗口与托盘统一；代价是"谁管谁"的边界必须写清楚（见批次 1 与 D4）。

## 6. 技术选型（决策点）

> 直接回 "D1 选①、D2 选①…" 即可。

### D1 托盘程序怎么做？  ✅ **已决定：②**

| 选项 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **① 建议** | Python 原生：`pystray` + `Pillow`，**与后端同进程** | 改动最小、代码全复用、能直接弹通知 | 观感朴素（够用） |
| ② | 保留 Tauri 壳 + 加系统托盘 | 原生观感更好 | 要管理 Python sidecar、跨语言传状态，复杂，且桌面壳代码要重写 |

**选了 ② 之后，有三件事是固定的：**

| 项 | 说明 |
| --- | --- |
| 托盘写在 Rust 侧 | 用 Tauri v2 自带的 `TrayIcon`（`desktop/src-tauri` 里加代码），不是 `pystray` |
| Python 保持子进程 | 现有 `lib.rs` 已经在 spawn 后端并转发 stdout/stderr，这条保留 |
| exe 必须在工作区外 | 本机已证实：工作区内的 exe 会被降权。落点继续用 `%USERPROFILE%\wechat-bot\` |

**D4 的退出语义因此更关键**：托盘"退出"必须同时结束 Python 子进程并写下停止标记，否则看门狗会把整个壳再拉起来。

### D2 要不要打包成单 exe？

| 选项 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **① 建议先做** | 不打包，保留 conda 环境，用一个 exe / 快捷方式启动 | 立刻可用、不踩坑 | 仍依赖该环境（换机器要重建） |
| ② | PyInstaller 打包 | 彻底独立 | `wechatauto-replica` 可能有隐式资源 / 动态导入，容易卡住 |

**建议：批次 1–3 用 ①，批次 4 再评估 ②。别让打包挡住前面的成果。**

### D3 手机端要不要上 HTTPS？

| 选项 | 效果 |

### 批次 2.5：把「预热」做成真的（反馈「他怎么一直在连接啊」的后续）

起因：连接微信一次要 55～76 秒，希望"到图书馆点一下就是秒开"。查证后发现两件事：

1. **预热本来就有**：`BOT_AUTOREPLY_ON_START=0` 时 `main.py` 开机就调 `connect()`，
   那 76 秒在开机时已经付掉了，并不是等你点按钮才付。
2. **76 秒花在哪**：`wechatauto` 的 `AddListenAll(discover=False)` → `db.Listener.add_all()`
   → `db.get_sessions(limit=500)`。解密结果其实缓存在 `%TEMP%\wechatauto_db\`（120MB 那份
   至今仍是 09-26 的），但微信不停 checkpoint 改写主库，缓存随时失效，所以**每个后端进程
   启动一次就得重来一遍**。这是第三方库的内在成本，本批次不动它。

真正缺的是"可靠"和"看得见"：

| 改动 | 说明 |
| --- | --- |
| 新增 `BotController.warm_up()` / `_warm_loop()` | 后台连微信；失败按 `WARM_BACKOFF`（15s→30s→60s→120s→300s 封顶）自动重试，直到连上 |
| 改 `src/main.py` | `_boot()` 改用 `warm_up()`；自动回复开启失败时也交给预热线程重试（`auto_start=True`），连上就开 |
| 改 `snapshot()` | 新增 `starting_seconds` 与 `warm: {state, attempts, error, retry_in}` |
| 改 `web/index.html` | 状态细分：运行中 / 连接中（**已等待 N 秒**）/ 待命中（微信已连好）/ 未连上（已试 N 次，M 秒后自动重试）/ 已暂停；圆点四色；新增 `warm_ready` 原因码 |
| **修 bug** | `start()` 在 `_starting` 期间直接 `return True` 却不记意图 —— 连接途中按「开始回复」那一下等于没点，永远不会开始。现在用 `_want_running` 记住它，`stop()` 会取消 |

**验收**（`tests/test_controller.py` 新增 5 个测试）：
- 预热成功 → `warm.state == "ready"`、`running` 仍为 `False`、动态里只有 `warm_ready`
  （不会像以前 `start()+stop()` 那样留下假的「已开启/已暂停」）。
- 前两次连不上、第三次成功 → `attempts == 3`，退避生效（测试里把 `WARM_BACKOFF` 调到 0.05s）。
- 连接途中按「开始回复」→ 连接完成后自动开始（回归测试锁住上面那个 bug）。
- 面板四种文案用无头 Edge 实际渲染验证过。

> 结论：**开机后到出门前这段时间，微信应该已经连好了**，面板会直接告诉你"待命中"，
> 那时点「开始回复」是秒开的。若显示"微信还没连上（已试 N 次）"，说明微信没启动或没登录，
> 它会自己一直重试，你到了地方再点也不会卡在连接上。

### 批次 2.6：收消息提速（A）+ 白名单落地（B）

> 触发反馈：「有时候消息没法及时接收到是为什么？有时候很快就收到消息然后回复，有时候又很久。」

#### A. 收消息为什么"有时快有时慢"

读取路径原本用 wechatauto 的 `AddListenAll` —— 它给**每个会话**注册一个监听对象，
轮询线程每轮逐个会话查一次新消息，而**每一次查询都要把每个消息分片库各打开一次**。
本机 500 个会话，实测**一轮 40～50 秒**（约 82ms/会话）。

而会话表是按"最近有往来"排序的，轮询也按这个顺序走，于是：

- 正在跟你聊天的人排在**最前面** → 一轮刚开始就轮到他 → **几秒就回**；
- 好久没联系的人排在几百名之后 → 要等整轮走完 → **最长 40 多秒**；
- 微信一写库还会让解密缓存失效，那一轮要顺带重建几十 MB 的副本（单库校验就要 2～4 秒），更慢。

**改法：会话表差分轮询。**

| 改动 | 说明 |
| --- | --- |
| 重写 `src/wechat_client.py` 读取侧 | 不用 `AddListenAll`。每轮先用 `get_sessions()`（一次查询 ~20ms）看哪些会话的 `last_time / unread / summary` 变了，**只对这几个会话**查消息。实测一轮 40～50 秒 → **0.02～0.06 秒** |
| 同上 | **第一轮只登记 500 个会话的指纹、一个消息库都不打开**（曾经写成"第一次见到就锚定水位"，等于把 40 秒挪到后台，照样堵住新消息——已改掉并由测试钉住） |
| 同上 | 启动**不再遍历 500 个会话的消息库** → 大分片库改成"真有新消息时才打开" |
| 同上 | 第一次见到某个会话（启动那一刻）只锚定水位，**不回放**启动之前的历史消息；水位按 `sort_seq` 逐条推进，连发几条也不会漏 |
| 同上 | 单个会话查库报错只跳过它，不拖垮整轮；群聊在读取侧直接不查 |
| 改 `src/controller.py` | 日志新增**发现延迟**（对方发出 → 我们读到），这是灵敏度的直接指标 |
| 重写 `tests/test_wechat_client.py` | 假消息库 + 差分/水位/不回放历史/连发不漏/坏库不拖垮整轮 的回归测试 |

**实测验收（2026-10-05 15:13 重启后）**：

- `[启动] 连接微信窗口 1.5s + 起轮询 0.0s = 合计 1.5s`（改前 **60.5s**）
- 预热：`第 1 次尝试，耗时 1.6s`（改前 **61.8s**）——**顺手解决了"他怎么一直在连接"的另一半**
- 一轮轮询实测 **0.015 / 0.029 / 0.059 秒**（500 个会话，改前 41～50 秒）
- 发现延迟 ≈ 轮询间隔（0.5s）+ 读一条消息（~0.1s）→ **1 秒内**，且**与排在会话表第几无关**
- 顺带收益：轮询线程的占用从"几乎 100% 时间都在读库"降到 ~5%，磁盘/CPU 噪声显著下降

### 批次 4.5：启动/退出路径的三个坑（2026-10-05 实测）

引子：三哥问「电脑我好像退了，在哪里启动」—— 他点了托盘里的「退出」。
查现场时发现不止"退出后要手动启动"这一件事，还有两个更隐蔽的问题：

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 从托盘点了「退出」，约 30 秒后程序**自己回来了** | 看门狗 `break` 出循环时没有显式 `exit 0`；计划任务配了 `RestartCount=3`（失败重试），调度器把"用户主动退出"当成脚本失败，于是又拉了一遍。日志里能看到 `16:04:55 正常退出` 紧跟着 `16:05:29 又开始拉起` | `scripts/backend-loop.ps1` 的退出分支补 `exit 0`；用 `BOT_SHELL_EXE=whoami.exe` 当假壳实测：脚本退出码由非 0 变为 **0** |
| 同时跑着**两个看门狗**，抢着拉壳 | 壳还活着时又触发了一次任务（或手动开了 `desktop.exe`），看门狗并不知道，于是又拉一个壳；两个壳抢 8000 端口（`ControlServer` 刻意关掉了 `SO_REUSEADDR`），后启的必然绑定失败 → 失败-重试循环 | 看门狗启动时先看有没有 `desktop` 进程，已有就记一行日志并 `exit 0`；宁可少一个看门狗，也不重复拉壳、也不复活用户主动的退出 |
| 计划任务"启动成功"但面板起不来（`LastTaskResult=1`） | 改 `backend-loop.ps1` 时**丢了 UTF-8 BOM**。PowerShell 5.1 对无 BOM 的 .ps1 按系统 ANSI 代码页（这里是 GBK）解码，中文注释破坏了引号配对，第 39 行起整个脚本语法错误 | 恢复 BOM；新增 `tests/test_scripts.py` 钉住"所有 `*.ps1` 必须带 BOM"、`*.cmd` 必须 CRLF 且不能带 BOM |

顺带交付"自己动手"的入口（回答"在哪里启动"）：

- 桌面快捷方式 **「启动自动回复」** → `scripts/start-backend.cmd`（内部就是 `schtasks /Run`）。
  托盘点过退出之后双击它即可，约 20 秒后面板可用；**什么都不做也行 —— 下次登录会自启**。
- `start-backend.cmd` 必须存成 **CRLF**：cmd.exe 不认 LF-only 批处理，会把相邻命令粘成一条，
  表现是一堆 `is not recognized` 却不说哪里错（当天真写错过一次，见测试）。

### 批次 4.7：群聊只回一个群（白名单 + 关键词，2026-10-05）

三哥要求：「对闲适老爸小屋这个群聊开通白名单，群聊只回复这个」。
先摸清了两件事，再动手：

| 发现 | 影响 |
| --- | --- |
| 原来的 `reply.whitelist` 是**人和群共用一份** | 直接把群名填进去会把所有好友也过滤掉 → 必须给群单开一份名单 |
| 群里最近 25 条消息**一个 @ 都没有** | `only_when_mentioned: true` 等于永远不吭声；三哥选了「提到关键词才回」 |

**配置**（`config.yaml` 的 `reply.group`，面板上也能改）：

```yaml
group:
  enabled: true            # 群聊总开关（关掉就不读群消息库）
  only_when_mentioned: true  # 配了 trigger_keywords 时以关键词为准，本项不生效
  whitelist: [闲适老爸小屋]  # 只回这些群；留空 = 所有群都回
  trigger_keywords: [三哥, 老三, 三弟]   # 群里命中任一关键词（或被 @）才回；留空 = 每条都回
```

**判断顺序**（`Bot.reject_reason`，群聊分支）：

```
群聊没开            → group_disabled
不在 group_whitelist → not_in_group_whitelist
配了关键词           → 命中关键词 或 被@ 才回，否则 group_keyword_not_matched
没配关键词           → 沿用 only_when_mentioned（默认"被@才回"）
```

群聊白名单只管群，好友那份 `whitelist` 不受影响；关键词同理。

**顺手修掉的一个真 bug：群消息正文带着 wxid**

消息库里群消息的 `content` 是 `<发送者 wxid>: 正文`。原来的读取路径原样透传，
大模型会看到「wxid_r0d6thwrcyuj22 说：wxid_r0d6thwrcyuj22: 不烧心」，既认不出人，
前缀还会污染关键词判断。现在读取时剥掉前缀、把 wxid 换成微信备注名（`_display_name`）。

#### 附：发送其实成功了，库却报「发送失败」

为了验证群聊这条路，第一次实测发送（发给自己的「文件传输助手」）时发现：
`SendMsg` 返回「发送失败：多次重试未完成」，可消息**已经躺在对方聊天里了，而且是两条**。

| 路径 | 表现 |
| --- | --- |
| UIA（`uia.send_text`） | 一条、发完查库确认，返回 True ✅ |
| 回退路径（`click_send`） | 靠**截图/OCR**判断输入框是否清空；微信窗口最小化或不在前台时误判 → 重发 → 报错 ❌ |

实测：UIA 可用时 `open_chat`/`send_text`/`_verify_sent` 全 True，消息只落一条；
冷启动（UIA 还没就绪）那次走了回退路径，于是重复 + 报错。

**对策**：`WeChatClient.send` 现在带上 `chat_id`，库报错时回头查消息库——
只要有自己发的、内容一致、时间在本次发送之后的消息，就判定成功（记一条 warning），不再抛错、不再重试；
复核要等 5 秒（`_send_confirm_timeout`），复核不可用（拿不到库或老调用不传 `chat_id`）时维持原行为。

**运维结论**：让微信窗口保持**不最小化**，发送才稳定走 UIA 那条路；
真机全链路（有人发消息 → 自动回复落到对方聊天）还等一次实弹验证。

### 批次 4.8（热修）：所有消息都被静默丢掉 —— 中英文类型名不匹配（2026-10-05 18:40）

三哥原话：「奇怪好像不回复了 群里发的消息和私人发的消息都没回复怎么回事」。

**现场**：`running=True`、`warm=ready`、`last_error` 空、日志干净、进程 CPU 正常、
轮询每秒都在跑 —— 但「今日 回 0 · 跳过 0 · 出错 0」**一条记录都没有**。
也就是说：不是「回了没发出去」，而是消息**根本没进到机器人手里**。

**排查链**（每一步都留了实证，值得记下来）：

| 检查 | 结果 |
| --- | --- |
| 另起一个独立实例读消息库 | 能看到**当前**消息（群里 18:24 的「三犬」）→ 库是活的 |
| 常驻客户端轮询灵敏度 | 往文件传输助手发一条，**1 秒内**会话指纹就变了 → 轮询也是活的 |
| 后台进程 CPU | 15 秒涨 1.98s → 轮询线程没死、也不是空转 |
| 把群里真实那几行的原始字段打出来 | ❗ `type=文本` / `动画表情` / `系统消息`（中文），不是 `text` |

**根因**：`wechatauto` 的 `_export_row()` 把 `type` 填成**中文显示名**
（见 `wechatauto.db.MSG_TYPE_NAMES`：1=文本、3=图片、34=语音、43=视频、47=动画表情、
49=文件/链接/卡片、10000=系统消息）。而我们的读取映射写的是

```python
mtype = str(row.get("type") or "").lower()
if mtype not in {"text", "quote"}:   # ← 中文名永远不等于 text
    return None                        # ← 每条消息都在这里被静默丢掉
```

**这个 bug 从装好那天就在**，不是这一轮改出来的：收消息这条路
（真实消息 → 判断 → 回复）此前**从未真正跑通过**，所以「全链路实测」一直挂着。
它之所以能藏这么久，是因为丢弃路径**一句话都不打**：面板没记录、日志没异常、
状态显示运行中 —— 所有仪表都显示“正常”。

**修法**（`src/wechat_client.py`）：中英文名都认，再加数字 `type_code` 兜底。

```python
REPLYABLE_TYPES = frozenset({"text", "quote", "文本", "引用", "引用回复"})
REPLYABLE_TYPE_CODES = frozenset({1, 37, 105})  # 1 = 文本；37 / 105 = 引用回复

def is_replyable_type(row) -> bool: ...   # 名字命中 或 type_code 命中
```

**验证**：重启并恢复「运行中」后，100 秒内就抓到一条真实群消息
（另一个群）→ 正确跳过，理由 `not_in_group_whitelist`；
这是**第一次**有真实消息走完整条判断链。153 项测试通过（新增 4 项钉住中英文类型名）。

**教训**（写进代码注释了）：读取侧的每一次 `return None` 都是一个黑盒。
这次能定位，靠的是「把真实那一行的原始字段打出来看」，而不是继续读代码猜。
下一步可以做的：给「丢弃」按原因计数并露到面板，别再让它们无声无息。
### 批次 6：让「静默失灵」不可能再发生（2026-10-05 晚）

引子：批次 4.8 把收消息修通之后，三哥说「反正还有任务就继续」。
所以这一批不是新功能，而是把那天晚上最吓人的那一点堵死：

> **机器人失聪了一整晚，而面板、日志、状态全都显示正常。**

状态来自标志位，标志位不会因为线程死掉、消息被静默丢弃而变。
这一批补的就是「状态之外的事实」。

| 编号 | 做了什么 | 堵住哪一幕 |
| --- | --- | --- |
| 6.1 | `/api/status` 新增 `receive`：轮询心跳、最近一条消息距今、今日读到条数、正在跟多少会话 | 面板只会说「运行中」 |
| 6.2 | 读取侧每一次 `return None` 都按原因计数（自己发的 / 类型不支持 / 空内容 / 群开关关着 / 不在群白名单 / 非个人），面板显示「丢弃 N 条」 | 每条消息被静默丢掉，一个字都没留（4.8 的根因） |
| 6.3 | 群白名单**前移到读取侧**：名单外的群连消息库都不打开 | 别的群的消息一直在白名单外白白读一遍再丢 |

> **6.3 踩的坑（值得记）**：第一版用 `db.group_id_to_name()` 拿群名映射 —— 那个接口
> 要**单个群 id 当参数**，拿不到全量；于是映射一直是空的，而「拿不到群名就放行」的
> 保守策略让整个过滤**静默失效**：`drop_group_not_allowed` 恒为 0，别的群照样读。
> 全量接口是 `db.get_groups()`（本机 91 个群，每项有 `username`/`name`）。
> 教训和 4.8 一样：保守兜底 + 静默 = 假象；所以 `stats.group_filter` 现在把
> 「白名单几个、已知群名几个」直接露在面板上。
| 6.4 | 「守夜人」线程：每 30 秒看一次心跳，读取线程卡住或回复循环停摆超过 3 分钟 → 留痕 + 自动重连（10 分钟最多一次） | 状态写着运行中，实际没有任何线程在干活 |

面板上多了一行（状态卡片里、错误提示下面）：

```text
收消息：轮询 刚刚 · 最近一条 2 分钟前 · 今日读到 11 条 · 丢弃 3 条 · 在跟 42 个会话
```

疑似卡住时它会变红并直接给自救办法：

```text
⚠ 收消息：轮询 已停 · … —— 点上面的「重连」自救
```

**几个刻意的选择**：

1. **空白名单 = 不限制**：读取侧必须跟 `Bot.reject_reason` 用同一套语义。
   两处各写一套「空名单算不算全都回」，迟早会出现「读了不判」或「判了不读」的偏差。
2. **拿不到群名就放行**：`group_id_to_name()` 失败时宁可多读一个群，
   也不能因为查名失败漏掉该回的群。
3. **回复循环的卡死阈值是 3 分钟**：大模型慢的时候一次生成可能几十秒，
   阈值太紧会把正常等待当成卡死，然后重连 —— 那才是自伤。
4. **守夜人自己不能死**：它每轮自检都包在 try 里，出错只记一笔。

**验收**：167 项测试通过（批次 6 新增 14 项：读取侧 7、控制器 6、面板资产 1）。

| 轮询节奏 | `poll_rounds` 25 秒涨 45 轮 ≈ **0.55 秒/轮**（`get_groups()` 拉 91 个群名没有拖慢它） |

- `action` 取值：`replied` | `skipped` | `error` | `system`（`system` 是初稿没有的第 4 种：启停事件）

- 一条 `replied` 事件若 `reason == "llm_failed"`，说明 LLM 调用失败、发出去的是 `fallback_reply` 兜底话术

### 8.2 新增 `GET /api/lists` 与 `POST /api/lists`

```json
{ "whitelist": ["张三"], "blacklist": ["某微商"], "match_mode": "exact",
  "open_to_all": false, "only_person": true }
```

- `GET` 额外回一个 `open_to_all`（= 白名单为空）：**这是面板要红字警告的那件事**。
- `only_person` = 只回"个人"：群聊（另受 `reply.group.enabled` 控制）、公众号服务号（`gh_*`）、
  企业微信（`*@openim`）、微信系统号一律不回，在**读取侧**就挡掉（连消息库都不打开）。
  默认 `true`；改了立刻调 `WeChatClient.set_only_person()` 热传到轮询线程，不用重启。
- `POST` 只处理传进来的键，改完**立即生效**（bot 每次判断都现读 config，不重启进程）。
- 接受数组，也接受"换行 / 逗号 / 顿号 / 分号分隔"的字符串（手机上粘贴名单更顺手）；自动去重、去空白，上限 500 个。
- 持久化到 `lists.local.json`（**不改写带注释的 config.yaml**），下次启动时叠加覆盖 config.yaml。
- 名字按 `reply.match_mode` 匹配（默认 `exact`），填的是**聊天列表上显示的备注名**。

### 8.3 新增 `POST /api/reconnect`

手机上的自救入口：微信掉线、接口卡住时不用回家按键盘。

```
POST /api/reconnect        （无 body）
→ {"ok": true, ...snapshot()}   // 立刻返回，不阻塞
```

语义：

| 情况 | 行为 |
| --- | --- |
| 正在连接中（`starting`） | 返回 `ok: false`，不插一脚 —— 否则会变成两份整库解密 |
| 原来在回复 | 停循环 → 换掉微信对象 → 重连 → 自动恢复回复 |
| 原来暂停 | 只重连，保持暂停 |
| 重连失败 | 交给预热退避重试（`warm.state` 变 `waiting`），并记一条 `prepare_failed` |

进度看 `GET /api/status` 的 `warm.state`（`connecting → ready`）。
实测（2026-10-05）：连接本来就热，重连 3 秒完成；动态里留下 `reconnecting → reconnected` 两条。
